# 082: PricingResult rehydrated from DB with one-field validation, then cast

## Problem Statement

`src/twilio-webhook.ts:152` rehydrates a stored pricing blob with
`pricing = rawP as PricingResult` after validating exactly one field --
`typeof rawP.quote_price === "number"` (line 148) -- and hands the result
straight to `runEditPipeline` (line 161). Every other field on the interface
(`format`, `budget`, `tier_key`, `duration_hours`, `anchor`, `floor`) crosses
the persistence boundary unchecked.

The reachable consequence: a row whose `pricing_json` carries
`format: "unresolved"` together with `budget.tier: "no_viable_scope"` passes
both guards in `buildBudgetModeBlock` and reaches
`findMinFloor(pricing.format as Format, ...)` (`src/prompts/generate.ts:383`).
There, `RATE_TABLES["unresolved"]` is `undefined` -- `"unresolved"` is a member
of `RecommendedFormat`, not of `Format` (`src/types.ts:9-24`) -- and
`Object.entries(rateTable)` (`generate.ts:442`) throws
`TypeError: Cannot convert undefined or null to object`.

**Pre-existing, not a regression.** **Fails loud (throw), not silent (wrong
price).** The throw is already caught by the handler wrapper
(`twilio-webhook.ts:270-274`), so the process does not crash: Alex gets
`Error editing lead #N. Check server logs.` and that lead's SMS edit loop is
dead until the row is repaired. No wrong quote is ever generated by this path.

**Found by:** code review (persistence-boundary pass)

## Findings

- `twilio-webhook.ts:145` validates `classification.mode` is a string;
  `:148` validates `pricing.quote_price` is a number. Nothing else.
  `:151-152` then cast both blobs to their full interfaces.
- `twilio-webhook.ts` is the **only** place a rehydrated pricing blob is fed
  back into the pipeline. The sibling reader `src/utils/shape-lead.ts:15` uses
  `safeJsonParse` into `Record<string, unknown>` and only reads fields for
  display, so it is not exposed.
- Neither guard ahead of the crash site can stop this combination:
  - `generate.ts:337` gates on **classification** fields
    (`action === "one_question" && format_recommended === "unresolved"`), not on
    `pricing.format`. The two blobs are parsed independently and can disagree.
  - `generate.ts:342` returns early only when `budget.tier === "none"`.
- `findMinFloor` (`generate.ts:434-450`) does no `if (!rateTable)` check before
  `Object.entries`. Its sibling `lookupPrice` **does** --
  `price.ts:57-59` throws `PricingError('Cannot look up pricing for unresolved
  format')` and `price.ts:62-66` throws
  `No rate table for format "X". Available: ...`. The precedent for the fix is
  already in the repo, one file over.
- **The write side is currently sound**, which is why this needs a corrupt or
  hand-edited row to fire. Both producers of `format: "unresolved"` hardcode
  `budget: { tier: "none" }` -- `createClarificationPricingResult`
  (`run-pipeline.ts:33-44`) and the hard-gate decline
  (`run-pipeline.ts:136-146`) -- and `detectBudgetGap` is only ever called under
  `format !== "unresolved"` (`run-pipeline.ts:196-197`, `:210-213`). The
  invariant comment at `generate.ts:373-382` describes this accurately.
- What the invariant does not cover: rows written by an older schema, a manual
  SQL edit, a restored backup, or a future write path that sets `budget` and
  `format` independently. The invariant lives on the write side; the read side
  trusts it with a cast and has no way to notice when it stops holding.
- **Open question, unresolved at filing time (affects the test, not the fix):**
  it was not verified whether any lead row can reach `status: "sent"` carrying a
  `pricing_json` with `format: "unresolved"`. `handleEdit` only proceeds via
  `resolveLead`, which requires `status === "sent"` (`twilio-webhook.ts:68`). If
  clarification-first and hard-gate-decline leads never land in `"sent"`, the
  whole unresolved-format family is unreachable through this handler regardless
  of budget tier, and both fixes below are purely defensive against future write
  paths. Check `src/post-pipeline.ts` and `src/automation/orchestrator.ts`
  before writing the regression test -- if the answer is "never", the test must
  construct a row state the system does not otherwise produce.

## Proposed Solutions

### Option A: Validate the branching-critical fields at the rehydration boundary (Recommended)

Extend the existing guard in `twilio-webhook.ts` to check the fields that
actually steer control flow, so a bad row is rejected by the handler's own
"corrupt stored data" path (`:153-156`) instead of throwing three frames deep.

```typescript
const VALID_BUDGET_TIERS = ["none", "small", "large", "no_viable_scope"];
if (
  typeof rawP !== "object" || rawP === null ||
  typeof rawP.quote_price !== "number" ||
  typeof rawP.format !== "string" ||
  typeof rawP.tier_key !== "string" ||
  typeof rawP.budget !== "object" || rawP.budget === null ||
  !VALID_BUDGET_TIERS.includes(rawP.budget.tier) ||
  (rawP.format === "unresolved" && rawP.budget.tier !== "none")
) {
  throw new Error("invalid pricing shape");
}
```

The last clause is the invariant from `generate.ts:373-382` written as an
executable check rather than a comment.

- **Pros:** fails at the boundary with the message Alex already expects
  (`Lead #N has corrupt stored data. Check dashboard.`); encodes the invariant
  where it can be enforced; no change to the hot path.
- **Cons:** the boundary check must be kept in step with `PricingResult`; a
  narrow allow-list could reject a row a future schema legitimately writes.
- **Effort:** Small | **Risk:** Low

### Option B: Guard inside `findMinFloor`

Add the `lookupPrice` guard to `findMinFloor`:

```typescript
const rateTable = RATE_TABLES[format];
if (!rateTable) {
  const available = Object.keys(RATE_TABLES).join(", ");
  throw new Error(`No rate table for format "${format}". Available: ${available}`);
}
```

- **Pros:** matches `price.ts:62-66` exactly; protects every caller, not just
  the SMS edit path; turns an opaque `TypeError` into a message that names the
  bad value.
- **Cons:** still throws, just legibly -- the lead's edit round still fails, and
  the failure still surfaces to Alex as the generic "check server logs" SMS.
- **Effort:** Small | **Risk:** None

### Option C: Do nothing, document the exposure

The write side is provably sound today and the failure is loud, caught, and
single-lead. Record it as accepted risk in the invariant comment.

- **Pros:** zero code change.
- **Cons:** leaves a `as PricingResult` cast standing on one validated field,
  and the cast gets weaker every time `PricingResult` gains a field.
- **Effort:** None | **Risk:** the invariant's enforcement stays a comment.

## Recommended Action

**A and B together** -- they are complementary, not alternatives. B is three
lines and makes the failure legible for every caller; A stops the bad row before
it costs a context-assembly round trip and puts the invariant somewhere it can
fail. Do B first: it is the smaller change and it is the one that makes the
diagnosis obvious if A's allow-list ever proves too narrow.
